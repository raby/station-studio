# Example stations

This directory holds the bundled station templates that ship with
Station Studio. Each is a working playlist generator, copied into
`~/.station-studio/stations/` on first boot.

**Read these in order if you're new:**

| File | What it is | When to fork |
|------|------------|---------------|
| [`starter.json`](starter.json) | Tiny, stateless, two strategies (`weighted` + `jingle`). Demonstrates the slot+strategy mental model on a one-week / one-track-per-hour grid (168 slots). | **Your first station.** Read this end-to-end before anything else; it has just enough complexity to be interesting and no cursor mechanics. |
| [`stateful-starter.json`](stateful-starter.json) | One persistent cursor (`sequential` strategy) + sprinkled `prev_ref` slots. 336 slots / week (every 30 min × 7 days), one content pool. Demonstrates **cross-week state**: cursor advances 24 positions/week, cycles every 14 weeks; prev_ref slots read from the previous week's playlist at the same position. | **Your second station, with state.** Read this after `starter.json` when you want to understand persistent cursors + prev_ref. Smaller and more focused than `rebirth-classics.json`. |
| [`rebirth-classics.json`](rebirth-classics.json) | One persistent cursor, `window` strategy. 3,010 slots / week, two content pools. First production-scale `row_template` station with cursor advance. | **Your third station.** Forking from here gives you a real cursor-driven rotation with row_template's per-day shape (vs `flat_slots`'s flat list). |
| [`rebirth-radio.json`](rebirth-radio.json) | Full feature surface: nine persistent cursors with cross-week advance, all five strategies (`jingle`, `weighted`, `mix`, `prev_ref`, `sequential`), reference role. 2,196 slots / week. | **Your fourth station** (or your reference for "can the engine do X?"). Forking from here is forking a complete production station — be ready for it. |

## Companion files (one per station)

For each station JSON, you may see one or more sibling files:

| Suffix | Purpose |
|--------|---------|
| `.editor.json` | Auto-derived **editor sidecar** (§16.2.1) — section grouping + macro detection for the visualiser. Regenerate via `python -m scripts.derive_sidecar --station NAME.json --out NAME.editor.json` if the template changes. |
| `.pool-manifest.json` | Optional **pool manifest** (§14.36) — declares which iTunes XML files supply which named source pool. Picked up by `make import-weekly-pools manifest=...`. |
| `*.itunes.xml` | **Synthetic companion pool** for the two starter stations (§16.14 + §16.14.t1). Imported automatically on first boot when the SOURCES table is empty. |

## Regenerating the starter pools

The two starter stations' XML pools are generated deterministically
by small scripts — fix a typo or change the track count in one
place, then run the matching Make target:

| Station | Pools | Command | Generator script |
|---|---|---|---|
| starter | `STARTER_CONTENT` (50 tracks / 10 artists), `STARTER_JINGLES` (5 tracks) | `make refresh-starter-pools` | [`scripts/generate_starter_pools.py`](../scripts/generate_starter_pools.py) |
| stateful-starter | `STATEFUL_CONTENT` (336 tracks / 14 artists, exact cycle match) | `make refresh-stateful-starter-pools` | [`scripts/generate_stateful_starter_pools.py`](../scripts/generate_stateful_starter_pools.py) |

The XML files in this dir are regenerated byte-identically.

## How to add jingles to `stateful-starter`

The stateful starter ships **without** jingles to keep the
teaching surface focused on persistent cursors. If you want to
add them once you've understood the cursor mechanic, the
recipe is short:

1. Add `STARTER_JINGLES` to `stateful-starter.json`'s `sources`
   list — the same pool the §16.14 starter uses is already
   auto-imported on first boot, so you don't need a new XML or
   a new import step:
   ```jsonc
   "sources": [
     { "name": "STATEFUL_CONTENT", "colour": "#06d6a0", "role": "content" },
     { "name": "STARTER_JINGLES",  "colour": "#fb8500", "role": "content" }
   ]
   ```
2. Replace one or more slot entries with the jingle block shape
   from [`starter.json`](starter.json):
   ```jsonc
   { "source": "STARTER_JINGLES", "strategy": "jingle", "size": 1, "genre": "Jingle" }
   ```
   For a real radio-shape, swap `sequential` slots for jingles on
   a regular cadence. **Watch out for the existing `prev_ref`
   slots at positions 12, 24, 36, …, 324** — if you clobber
   those, you lose the prev_ref demo (which is fine if that's
   not what you're keeping). The simplest safe pattern: every 12
   starting at **6** — slots 6, 18, 30, …, 330 fall halfway
   between the prev_ref slots, never conflict, give you 28
   jingles spread evenly. For a denser jingle cadence (say, two
   per hour at :15 and :45 of every hour), swap positions
   `6 + 12·k` AND `9 + 12·k` for `k` in 0..27 — 56 jingles, all
   safely between prev_ref slots.
3. Drop `stateful-starter.editor.json` (so the sidecar
   auto-derive picks up your new structure), then restart
   `station-studio serve`.

The engine doesn't care that the jingles come from a pool used
by a different station — pools are pool names + tracks, nothing
else.

## What does `role: reference` mean?

Every entry in a station's `sources[]` block carries a
`role: "content"` or `role: "reference"` tag. The two roles
have very different engine behaviour:

* **`role: content`** — the engine samples from this pool.
  Every content-sampling strategy (`weighted` / `window` /
  `sequential` / `jingle` / `mix` / `prev_ref`) picks tracks
  from one of the template's content sources. If you write a
  slot block, it must point at a content source.
* **`role: reference`** — the engine NEVER samples from this
  pool. The implementation: `engine/persistence.py:load_pools`
  enumerates only `template.content_source_names`, which
  excludes reference-role entries. The pool is loaded into the
  DB by the importer (or the bootstrap's first-boot auto-import)
  but the generator silently skips it.

### Why is this distinction so thin?

Honestly: today, **it mostly isn't**. `role: reference` does
three things and only three things:

1. **Documents intent.** Other readers of your template (or you
   in six months) see that the pool is part of the station's
   declared world, even if no slot uses it.
2. **Shows in the UI.** The station detail page renders the full
   `sources[]` block in a "Source pools" panel; reference-role
   pools appear there with their colour + role tag.
3. **Triggers two safety rails (§14.35 cross-check).** This is
   the engine behaviour that actually matters today:
   * **At parse time** (`engine/template.py:parse_template`):
     if a slot block in the layout references a source whose
     role is `reference`, parsing fails with a `TemplateError`.
     You can't even write a template that points a content
     strategy at a reference pool.
   * **At generation time**
     (`engine/persistence.py:load_pools`): if the template
     declares a source as content but the imported DB pool
     was tagged `role="reference"`, generation fails with the
     same exception class. This catches the case where you
     fixed your template but forgot to re-import the pool with
     the corrected role.

### The canonical example

`starter.json`'s `sources[]` (§16.14.t3) ships with three
entries:

```jsonc
"sources": [
  { "name": "STARTER_CONTENT",   "colour": "#3a86ff", "role": "content"   },
  { "name": "STARTER_JINGLES",   "colour": "#fb8500", "role": "content"   },
  { "name": "REFERENCE_ARCHIVE", "colour": "#9b9b9b", "role": "reference" }
]
```

`REFERENCE_ARCHIVE` is declared but used in zero slot blocks.
The companion `starter-reference.itunes.xml` (12 synthetic
tracks total: 9 archive-only across 3 "archive artists" with
Genre=Archive, plus 3 "content echoes" — see the §16.14.t5
section below) auto-imports on first boot like the other
starter pools. The generator never *samples* from it as a slot
pool; the safety rails catch you if you try. The §16.14.t5
`cross_pool_dedup_sources` rule DOES read from it at
generation time (to build the exclusion set for `weighted`),
which is the role's first real engine use — see the new
section a few hundred lines down.

### Try the safety rail yourself

Open `stations/starter.json` (or, on a wheel/docker install, the
copy at `$STATION_STUDIO_HOME/stations/starter.json`), find the
first entry in `flat_slots`, replace its `"source"` value with
`"REFERENCE_ARCHIVE"` (e.g. change the first `{ "source":
"STARTER_JINGLES", ... }` to `{ "source": "REFERENCE_ARCHIVE",
"strategy": "weighted", "size": 1 }`). Restart `station-studio
serve`.

To see the rail fire, hit:

```bash
curl -X POST http://localhost:8001/api/stations/starter/generate \
  -H "Content-Type: application/json" \
  -d '{"week": 1}'
```

You get a `400 Bad Request` with a JSON body whose `detail`
field carries the `TemplateError` message — something like
`"block uses source 'REFERENCE_ARCHIVE' with role 'reference';
only 'content' sources can be referenced by the layout"`. That's
the parse-time guard firing. The "Generate next week" button on
the station detail page hits the same endpoint and surfaces the
same error in the UI's error toast.

**Heads-up on the sidecar.** The parse-time guard ALSO fires
during the lifespan's auto-seed step that runs on every restart
— the lifespan catches the exception and continues (so the
server still comes up), but the broken starter row doesn't get
seeded. Check the serve log if you don't see the curl error you
expect; the parse error often surfaces there as a warning before
your first request.

Also: editing `starter.json` does NOT auto-refresh the matching
`starter.editor.json`. The bootstrap's auto-derive helper fills
MISSING sidecars but won't refresh stale ones. If you also want
the visualiser to reflect the broken state, delete
`starter.editor.json` along with your edit — the auto-derive
fires on next boot and rebuilds it from the new template.

**To revert:** dev-clone users `git checkout
stations/starter.json stations/starter.editor.json`. Wheel/
docker users delete BOTH files and restart `station-studio
serve` — bootstrap re-seeds the original station and re-derives
its sidecar from the bundled copy on next boot.

### Cross-pool dedup with `cross_pool_dedup_sources` (§16.14.t5)

The first real engine use of `role: reference`: name reference
pools whose tracks the `weighted` strategy must exclude from
its pick set. Hobbyist framing: "never play anything that's
also in my MASTER_ARCHIVE."

**The starter ships with the demo wired up declaratively.** Open
`stations/starter.json` and you'll see (§16.14.t9):

```json
{
  "station": "starter",
  "name": "Starter Station — 168 slots (hourly, Mon→Sun)",
  ...,
  "rules": {
    "cross_pool_dedup_sources": ["REFERENCE_ARCHIVE"]
  },
  ...
}
```

When you run `station-studio serve` for the first time, the
auto-import lands all three starter pools, and the seeder reads
the `rules:` block and writes the row to the DB.

The starter's `REFERENCE_ARCHIVE` pool is 12 tracks: 9 archive-
originals (the §16.14.t3 teaching tracks) plus 3 "content
echoes" — byte-identical copies of `STARTER_CONTENT` entries
at counters 1, 25, and 50 (start / middle / end of the content
pool). Same Persistent ID in both XMLs → the importer's
dedup-by-PID logic gives you a single `Track` row that lives in
both `SourcePlaylist` rows.

Result: generate week 1 on the starter and the 3 echoed PIDs
NEVER appear in the playlist. The weighted strategy gets a
49-then-47 effective pool (we drop 3 of 50 content tracks) and
spreads the rest across the 147 weighted slots per the usual
shuffle-bag + artist-dedup math.

Verify with:

```bash
curl -X POST http://localhost:8001/api/stations/starter/generate \
  -H "Content-Type: application/json" \
  -d '{"week": 1}' | jq '[.entries[].track.persistent_id] |
                          map(select(. == "STCONT000000000001" or
                                     . == "STCONT000000000019" or
                                     . == "STCONT000000000032"))'
```

Output: `[]`. Without the rule, those 3 PIDs would land
several times across the 147 weighted picks (shuffle-bag
guarantees every track plays once per cycle).

#### The `rules:` block (§16.14.t9)

Templates declare per-station rule values in a top-level
`rules:` dict. Two value shapes are supported:

```json
"rules": {
  "artist_dedup_window": 15,                  // int rule
  "cross_pool_dedup_sources": ["ARCHIVE"]     // list rule
}
```

The parser looks each key up in the rules registry, validates
the value shape (int bounds + non-negative, list entries non-
empty + comma-free), and rejects bad shapes at parse time with
a `template.rules.<key>: ...` error. Unknown rule keys fail
with the list of valid keys included in the message.

**Operator wins after customisation.** When `seed_station`
applies the block, it writes a Rule row ONLY when no row
already exists for that (station_id, key). Once you customise
a rule (for int rules, that's `PUT
/api/stations/{slug}/rules/{key}`; for list rules, see the
API gap below), re-seeding leaves your value alone. The
template value is the **factory default**; the DB row is the
**live value**. They can diverge.

To **revert a rule to its factory default**: clear the Rule
row (for int rules via `DELETE
/api/stations/{slug}/rules/{key}`; for list rules see below),
then re-seed (next `seed_station` writes the template value
back). This is the documented escape hatch.

**`cat starter.json` shows factory defaults, not live values.**
For the live values of any rule (int or list), query
`GET /api/stations/starter/rules` — each row carries `kind`
(`"int"` or `"list"`), `value`, `default_value`, and
`is_override`.

**Rules CRUD endpoint covers both kinds (§16.14.t10).** All
three verbs work for both int and list rules:

```bash
# Read every rule, with kind discriminator + native value shape.
curl http://localhost:8001/api/stations/starter/rules

# Set a list rule.
curl -X PUT http://localhost:8001/api/stations/starter/rules/cross_pool_dedup_sources \
  -H 'content-type: application/json' \
  -d '{"value": ["ARCHIVE_A", "ARCHIVE_B"]}'

# Revert to the factory default (template value).
curl -X DELETE http://localhost:8001/api/stations/starter/rules/cross_pool_dedup_sources
```

Validation lives in `engine.rules` (`validate_int_rule_value`
+ `validate_list_rule_value`) and is shared with the template
parser, so the rules are identical whether you edit the JSON
or call the API:

* Int rules: non-negative, ≤ max_value, bool rejected
  explicitly (`{value: true}` 422s at the schema layer).
* List rules: each entry must be a non-empty string with no
  commas (the comma is the on-disk separator); whitespace
  stripped per entry.

Bad shapes return HTTP 400 with the validator's message
verbatim — operator typos surface where they happen.

**Frontend status (§16.14.t11).** The `<RulesPanel>` at
`/stations/{slug}/rules` renders BOTH int and list rules:

* **Int rules** keep the existing edit + save + reset UX
  (byte-identical to pre-§16.14.t10).
* **List rules** use the new chip editor (`<ListRuleRow>`).
  Each value is a chip with a × remove button; an "Add"
  input below lets the operator type a source pool name +
  press Enter (or pick from the reference-pool autocomplete
  suggestions). Save persists the new list; **Clear override**
  (rendered only when an override exists) DELETEs the Rule
  row.

**"Clear override" vs "Restore template default" (§16.14.t11
c1 review F1).** The chip editor's button is labelled
**Clear override** — not "Reset to default" — because what
it actually does is remove the Rule row from the DB. The
operator's NEXT GET will return the **registry default**
from `engine.rules.RULE_LIST_DEFAULTS` (today: `[]`), NOT
the template-declared default from `stations/starter.json`.
The template default reappears on the next `seed_station`
run (server restart or `make seed-stations`), because the
only-set-if-absent semantics re-apply the template's
`rules:` block. A helper line under the button names this
behaviour so the operator isn't surprised when the empty
state shows briefly + the template value returns on restart.

#### How to opt out of the starter's cross-pool dedup

Three paths in increasing permanence:

* **Easy clickable (§16.14.t11):** open
  `/stations/starter/rules`, find the
  `cross_pool_dedup_sources` row, click **Clear override**.
  Chips disappear, badge flips to "default." Caveat: the
  next server restart re-seeds the template value — this
  is the operator-wins / template-restart cycle. For
  permanent removal also do the JSON edit below.
* **API (programmatic):** `DELETE
  /api/stations/starter/rules/cross_pool_dedup_sources`.
  Same effect as the UI click.
* **Permanent:** edit `stations/starter.json` and remove
  the `rules:` block (or change `cross_pool_dedup_sources`
  to `[]`). Combine with the UI click / API DELETE above
  to clear the live row. After the next restart, the
  bootstrap auto-seed sees an empty `rules:` block + no
  Rule row → demo stays off.

#### How to add the rule to your own station

Just edit the station's JSON:

```json
{
  "station": "your-slug",
  ...,
  "rules": {
    "cross_pool_dedup_sources": ["YOUR_REFERENCE_POOL"]
  },
  ...
}
```

`make seed-stations` (or a server restart) reads the rule into
the DB. Each named pool must:
* be imported into the DB, AND
* have `role='reference'` on the `SourcePlaylist` row.

Both checks fail loud at generation time (HTTP 400) — the error
message names which check failed.

#### What the rule doesn't do today (deliberate punts)

* **Per-source semantics.** The exclusion set is a UNION across
  every named pool. Listing two reference pools with overlapping
  PIDs is fine but you can't say "exclude pool A from source X
  but not source Y." If you need that, file an issue.
* **Window strategy.** Only `weighted` excludes today. `window`
  (used by `prev_ref` fallbacks + some cursor-stateful templates)
  is queued as §16.14.t8 — file an issue if you need it.
* **Content-role sources.** D6 restricts the rule to reference
  pools. Naming a content pool would footgun the operator (a
  pool excluding itself starves the strategy). Loosening this
  would need self-reference detection logic.
* **Surfacing the template default separately from the
  registry default (§16.14.t11 c1 review F1).** GET
  `/api/stations/{slug}/rules` returns the registry default
  in `default_value`. The template's `rules:` block (the
  thing that auto-seeds on restart via only-set-if-absent)
  is NOT separately exposed — operators have to read the
  JSON file to see it. "Clear override" therefore drops to
  the registry default in the UI even when the template
  declared a richer factory default. Engine-side fix would
  surface both defaults in the API response; deferred to a
  future polish slice if it bites enough operators.

## Deeper jingle composition

The §16.14 starter teaches the basics — one jingle pool, jingles
every 8 slots. Real radio stations want more nuance: different
jingles for different dayparts, separate pools for hourly IDs vs
sweepers vs station tags, denser cadence in morning drive than
overnight. This section covers the patterns. All of them work
with TODAY's `jingle` strategy — no engine changes needed.

### The `jingle` strategy contract (the short version)

A jingle slot specifies a `source` (which pool to look in) AND a
`genre` (which Genre tag to filter for). The engine:

1. Loads the named source pool from the DB.
2. Filters tracks where `track.Genre == genre` (case-sensitive
   exact match).
3. Picks one — first matching track in deterministic mode (`rng:
   off`), `rng.choice(candidates)` in randomized mode (`rng: on`).
4. Fails LOUD if no track matches: `JingleGenreNotFoundError("no
   track with genre 'X'")`. There's no fallback, no nearest-match
   — your iTunes XML must have at least one track tagged exactly
   with the genre you ask for.

This contract is the only knob. Every pattern below is just a
different way of using it.

### Pattern 1 — One pool, multiple genres (the Rebirth Radio shape)

The simplest scaling pattern. One JINGLES pool holds every jingle
clip the station might use, each tagged with its appropriate
Genre. Different slot positions specify different genres:

```jsonc
"sources": [
  { "name": "JINGLES", "colour": "#fb8500", "role": "content" },
  { "name": "MUSIC",   "colour": "#3a86ff", "role": "content" }
],
"layout": {
  ...
  "flat_slots": [
    { "source": "JINGLES", "strategy": "jingle", "size": 1,
      "genre": "Daytime" },
    { "source": "MUSIC",   "strategy": "weighted", "size": 1 },
    { "source": "MUSIC",   "strategy": "weighted", "size": 1 },
    { "source": "JINGLES", "strategy": "jingle", "size": 1,
      "genre": "Mixzone" },
    ...
  ]
}
```

In iTunes you tag each jingle track with its appropriate Genre
(`Daytime`, `Mixzone`, `Hourly ID`, `Sweeper`, etc.). One XML
import; the engine filters per-slot.

This is how `stations/rebirth-radio.json` is structured — see
the `JINGLES` source + its `genre: "Daytime"` / `genre:
"Mixzone"` slots. Use this when:

* You have **one curator** for all jingles (single mental model).
* Genres are stable + well-defined ("daytime jingle" is a
  category you can imagine independently).
* You want the smallest number of pools in your `sources[]`.

### Pattern 2 — Multiple pools (the explicit-separation shape)

Each jingle type lives in its own pool:

```jsonc
"sources": [
  { "name": "HOURLY_IDS",  "colour": "#fb8500", "role": "content" },
  { "name": "SWEEPERS",    "colour": "#ffb703", "role": "content" },
  { "name": "STATION_TAGS","colour": "#fd8a09", "role": "content" }
],
"layout": {
  ...
  "flat_slots": [
    { "source": "HOURLY_IDS",   "strategy": "jingle", "size": 1,
      "genre": "Hourly" },
    ...
    { "source": "SWEEPERS",     "strategy": "jingle", "size": 1,
      "genre": "Sweeper" },
    ...
    { "source": "STATION_TAGS", "strategy": "jingle", "size": 1,
      "genre": "Tag" },
    ...
  ]
}
```

Each pool is one iTunes XML import via the Sources page. Use this
when:

* Different people maintain different jingle libraries (e.g.
  IDs come from a station imaging service, sweepers from a
  producer, tags from a designer).
* You want per-pool dedup or per-pool versioning — each XML is
  independently re-importable.
* The pool count matters more than the slot count (e.g. you
  rotate sweepers monthly; bumping `SWEEPERS` doesn't touch the
  other pools).

You still need `genre` on each block, even with separate pools.
The engine's contract is "filter tracks by genre"; if all your
sweepers carry `Genre: "Sweeper"` you can specify that and pick
deterministically per slot. If `SWEEPERS` has only one genre,
both `genre: "Sweeper"` and `genre: "Anything"` work as long as
the actual tracks carry the matching tag.

### Pattern 3 — Daypart cadence

There's no engine-level "daypart" concept. Dayparts are just
slot positions you choose to treat differently.

Pick the daypart boundary at design time. E.g. for a 168-slot
weekly template (one slot per hour, Mon→Sun):

* Slots 0-5, 18-23 = overnight (hours 0-5, 18-23 of each day)
* Slots 6-9 = morning drive
* Slots 10-13 = midday
* Slots 14-17 = afternoon

Pop different jingle blocks into different daypart slot positions:

```jsonc
"flat_slots": [
  // Overnight: just music, no jingles.
  { "source": "MUSIC", "strategy": "weighted", "size": 1 },
  // ... slots 1-5 ...

  // Morning drive: jingle every other slot ("hot clock").
  { "source": "JINGLES", "strategy": "jingle", "size": 1,
    "genre": "Morning ID" },
  { "source": "MUSIC",   "strategy": "weighted", "size": 1 },
  { "source": "JINGLES", "strategy": "jingle", "size": 1,
    "genre": "Morning ID" },
  // ...

  // Midday: jingle every 4 slots, different genre.
  { "source": "JINGLES", "strategy": "jingle", "size": 1,
    "genre": "Midday Sweep" },
  // ... etc.
]
```

The slot positions encode the daypart; the `genre` field per slot
encodes which jingle subset to draw from. You can combine pattern
1 (single pool, multi-genre) OR pattern 2 (multi-pool) with this
slot-position-as-daypart trick.

Use daypart cadence when:

* Different times of day deserve different vibes (morning drive
  high energy, overnight chill).
* You want SILENCE in some dayparts — just don't put any jingle
  slot in those positions.

### Pattern 4 — Programmed cadence (every Nth slot)

The §16.14 starter uses this: jingles every 8 slots, uniform
across the week. Simplest cadence; least configuration. Mixes
freely with patterns 1-3 (e.g. "every Nth slot is a jingle, and
the genre changes by daypart").

### Picking a pattern

| Situation | Use |
|---|---|
| One curator, one library, jingles tagged with Genre | Pattern 1 (one pool, multi-genre) |
| Multiple curators OR rotation cadences vary per type | Pattern 2 (multi-pool) |
| Time-of-day matters for jingle type or frequency | Pattern 3 (daypart cadence) |
| You're building your first multi-jingle station | Pattern 4 first; graduate to 1+3 |

### What `jingle` can NOT do today

Out of scope for this strategy as it exists:

* **Per-track rotation memory.** Jingle picks have NO history-
  aware exclusion. Track might be picked twice in a row by
  chance (rng=on) or always (rng=off, only one candidate).
  If you want "don't repeat the same ID twice in an hour," the
  workaround is more genres (split your IDs into ID_A / ID_B /
  ID_C and alternate slot genres) — a graduation problem this
  docs page doesn't solve.
* **Conditional jingles.** No "play sweeper X if previous slot
  was genre Y." Jingle picks are pure source-+-genre lookups.
* **Time-aware metadata.** No "play this jingle only on
  Mondays." If you want Mon-only IDs, that's a daypart pattern
  with a slot-position carve-out.

If one of these limitations actually bites your station, that's
the signal to file an issue — the docs page above stays accurate
as long as the strategy contract stays the same.

## Adding a new station

Drop `your-station.json` here. On next `station-studio serve`, the
auto-seed lifespan picks it up + creates the row. See
[CONTRIBUTING.md](../CONTRIBUTING.md) for the template grammar
contract and the slice pattern for proposing new station shapes.
