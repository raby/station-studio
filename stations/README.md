# Example stations

This directory holds the bundled station templates that ship with
Station Studio. Each is a working playlist generator, copied into
`~/.station-studio/stations/` on first boot.

**Read these in order if you're new:**

| File | What it is | When to fork |
|------|------------|---------------|
| [`starter.json`](starter.json) | Tiny, stateless, two strategies (`weighted` + `jingle`). Demonstrates the slot+strategy mental model on a one-week / one-track-per-hour grid (168 slots). | **Your first station.** Read this end-to-end before anything else; it has just enough complexity to be interesting and no cursor mechanics. |
| [`stateful-starter.json`](stateful-starter.json) | One persistent cursor (`sequential` strategy) + sprinkled `prev_ref` slots. 336 slots / week (every 30 min × 7 days), one content pool. Demonstrates **cross-week state**: cursor advances 24 positions/week, cycles every 14 weeks; prev_ref slots read from the previous week's playlist at the same position. | **Your second station, with state.** Read this after `starter.json` when you want to understand persistent cursors + prev_ref. Smaller and more focused than `rebirth-classics.json`. |
| [`rebirth-classics.json`](rebirth-classics.json) | One persistent cursor, `window` strategy. 3,010 slots / week, two content pools. First production-scale `row_template` station with cursor advance. | **Your third station.** Forking from here gives you a real cursor-driven rotation with row_template's per-day shape (vs `flat_slots`'s flat list). |
| [`rebirth-radio.json`](rebirth-radio.json) | Full feature surface: nine persistent cursors with cross-week advance, all five strategies (`jingle`, `weighted`, `mix`, `prev_ref`, `sequential`), reference role. 2,196 slots / week. | **Your fourth station** (or your reference for "can the engine do X?"). Forking from here is forking a complete production station — be ready for it. |

## Companion files (one per station)

For each station JSON, you may see one or more sibling files:

| Suffix | Purpose |
|--------|---------|
| `.editor.json` | Auto-derived **editor sidecar** (§16.2.1) — section grouping + macro detection for the visualiser. Regenerate via `python -m scripts.derive_sidecar --station NAME.json --out NAME.editor.json` if the template changes. |
| `.pool-manifest.json` | Optional **pool manifest** (§14.36) — declares which iTunes XML files supply which named source pool. Picked up by `make import-weekly-pools manifest=...`. |
| `*.itunes.xml` | **Synthetic companion pool** for the two starter stations (§16.14 + §16.14.t1). Imported automatically on first boot when the SOURCES table is empty. |

## Regenerating the starter pools

The two starter stations' XML pools are generated deterministically
by small scripts — fix a typo or change the track count in one
place, then run the matching Make target:

| Station | Pools | Command | Generator script |
|---|---|---|---|
| starter | `STARTER_CONTENT` (50 tracks / 10 artists), `STARTER_JINGLES` (5 tracks) | `make refresh-starter-pools` | [`scripts/generate_starter_pools.py`](../scripts/generate_starter_pools.py) |
| stateful-starter | `STATEFUL_CONTENT` (336 tracks / 14 artists, exact cycle match) | `make refresh-stateful-starter-pools` | [`scripts/generate_stateful_starter_pools.py`](../scripts/generate_stateful_starter_pools.py) |

The XML files in this dir are regenerated byte-identically.

## How to add jingles to `stateful-starter`

The stateful starter ships **without** jingles to keep the
teaching surface focused on persistent cursors. If you want to
add them once you've understood the cursor mechanic, the
recipe is short:

1. Add `STARTER_JINGLES` to `stateful-starter.json`'s `sources`
   list — the same pool the §16.14 starter uses is already
   auto-imported on first boot, so you don't need a new XML or
   a new import step:
   ```jsonc
   "sources": [
     { "name": "STATEFUL_CONTENT", "colour": "#06d6a0", "role": "content" },
     { "name": "STARTER_JINGLES",  "colour": "#fb8500", "role": "content" }
   ]
   ```
2. Replace one or more slot entries with the jingle block shape
   from [`starter.json`](starter.json):
   ```jsonc
   { "source": "STARTER_JINGLES", "strategy": "jingle", "size": 1, "genre": "Jingle" }
   ```
   For a real radio-shape, swap `sequential` slots for jingles on
   a regular cadence. **Watch out for the existing `prev_ref`
   slots at positions 12, 24, 36, …, 324** — if you clobber
   those, you lose the prev_ref demo (which is fine if that's
   not what you're keeping). The simplest safe pattern: every 12
   starting at **6** — slots 6, 18, 30, …, 330 fall halfway
   between the prev_ref slots, never conflict, give you 28
   jingles spread evenly. For a denser jingle cadence (say, two
   per hour at :15 and :45 of every hour), swap positions
   `6 + 12·k` AND `9 + 12·k` for `k` in 0..27 — 56 jingles, all
   safely between prev_ref slots.
3. Drop `stateful-starter.editor.json` (so the sidecar
   auto-derive picks up your new structure), then restart
   `station-studio serve`.

The engine doesn't care that the jingles come from a pool used
by a different station — pools are pool names + tracks, nothing
else.

## What does `role: reference` mean?

Every entry in a station's `sources[]` block carries a
`role: "content"` or `role: "reference"` tag. The two roles
have very different engine behaviour:

* **`role: content`** — the engine samples from this pool.
  Every content-sampling strategy (`weighted` / `window` /
  `sequential` / `jingle` / `mix` / `prev_ref`) picks tracks
  from one of the template's content sources. If you write a
  slot block, it must point at a content source.
* **`role: reference`** — the engine NEVER samples from this
  pool. The implementation: `engine/persistence.py:load_pools`
  enumerates only `template.content_source_names`, which
  excludes reference-role entries. The pool is loaded into the
  DB by the importer (or the bootstrap's first-boot auto-import)
  but the generator silently skips it.

### Why is this distinction so thin?

Honestly: today, **it mostly isn't**. `role: reference` does
three things and only three things:

1. **Documents intent.** Other readers of your template (or you
   in six months) see that the pool is part of the station's
   declared world, even if no slot uses it.
2. **Shows in the UI.** The station detail page renders the full
   `sources[]` block in a "Source pools" panel; reference-role
   pools appear there with their colour + role tag.
3. **Triggers two safety rails (§14.35 cross-check).** This is
   the engine behaviour that actually matters today:
   * **At parse time** (`engine/template.py:parse_template`):
     if a slot block in the layout references a source whose
     role is `reference`, parsing fails with a `TemplateError`.
     You can't even write a template that points a content
     strategy at a reference pool.
   * **At generation time**
     (`engine/persistence.py:load_pools`): if the template
     declares a source as content but the imported DB pool
     was tagged `role="reference"`, generation fails with the
     same exception class. This catches the case where you
     fixed your template but forgot to re-import the pool with
     the corrected role.

### The canonical example

`starter.json`'s `sources[]` (§16.14.t3) ships with three
entries:

```jsonc
"sources": [
  { "name": "STARTER_CONTENT",   "colour": "#3a86ff", "role": "content"   },
  { "name": "STARTER_JINGLES",   "colour": "#fb8500", "role": "content"   },
  { "name": "REFERENCE_ARCHIVE", "colour": "#9b9b9b", "role": "reference" }
]
```

`REFERENCE_ARCHIVE` is declared but used in zero slot blocks.
The companion `starter-reference.itunes.xml` (9 synthetic tracks
across 3 "archive artists", Genre=Archive) auto-imports on first
boot like the other starter pools. The generator never picks
from it; the safety rails catch you if you try.

### Try the safety rail yourself

Open `stations/starter.json` (or, on a wheel/docker install, the
copy at `$STATION_STUDIO_HOME/stations/starter.json`), find the
first entry in `flat_slots`, replace its `"source"` value with
`"REFERENCE_ARCHIVE"` (e.g. change the first `{ "source":
"STARTER_JINGLES", ... }` to `{ "source": "REFERENCE_ARCHIVE",
"strategy": "weighted", "size": 1 }`). Restart `station-studio
serve`.

To see the rail fire, hit:

```bash
curl -X POST http://localhost:8001/api/stations/starter/generate \
  -H "Content-Type: application/json" \
  -d '{"week": 1}'
```

You get a `400 Bad Request` with a JSON body whose `detail`
field carries the `TemplateError` message — something like
`"block uses source 'REFERENCE_ARCHIVE' with role 'reference';
only 'content' sources can be referenced by the layout"`. That's
the parse-time guard firing. The "Generate next week" button on
the station detail page hits the same endpoint and surfaces the
same error in the UI's error toast.

**Heads-up on the sidecar.** The parse-time guard ALSO fires
during the lifespan's auto-seed step that runs on every restart
— the lifespan catches the exception and continues (so the
server still comes up), but the broken starter row doesn't get
seeded. Check the serve log if you don't see the curl error you
expect; the parse error often surfaces there as a warning before
your first request.

Also: editing `starter.json` does NOT auto-refresh the matching
`starter.editor.json`. The bootstrap's auto-derive helper fills
MISSING sidecars but won't refresh stale ones. If you also want
the visualiser to reflect the broken state, delete
`starter.editor.json` along with your edit — the auto-derive
fires on next boot and rebuilds it from the new template.

**To revert:** dev-clone users `git checkout
stations/starter.json stations/starter.editor.json`. Wheel/
docker users delete BOTH files and restart `station-studio
serve` — bootstrap re-seeds the original station and re-derives
its sidecar from the bundled copy on next boot.

### Forward-looking utilities (not shipped)

The reference role's value scales as the engine grows. Three
slices are queued in `DESIGN.md` (each with its own trigger):

* **Cross-pool dedup (§16.14.t5)** — exclude tracks that
  appear in a reference pool from the content sampler's pick
  set (e.g. "never play anything already in my
  MASTER_ARCHIVE"). Trigger: a hobbyist asks for "exclude
  archive tracks from the rotation."
* **Master-archive `prev_ref` (§16.14.t6)** — let `prev_ref`
  slots read from a curated reference pool instead of the
  previous week's generated playlist. Trigger: a real station-
  template author asks for the master-archive read pattern.
* **Allowlist enforcement (§16.14.t7)** — restrict the content
  sampler to tracks that ALSO appear in a reference pool,
  treating it as a positive filter. Trigger: a hobbyist asks
  for the positive-filter pattern.

None shipped today; if you're reading this and one of those
landed, the slice that landed it should have rewritten this
paragraph + removed the corresponding watch-list entry.

## Adding a new station

Drop `your-station.json` here. On next `station-studio serve`, the
auto-seed lifespan picks it up + creates the row. See
[CONTRIBUTING.md](../CONTRIBUTING.md) for the template grammar
contract and the slice pattern for proposing new station shapes.
